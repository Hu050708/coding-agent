# 02 - 对照 PDF 理解五个自研核心

## 1. PDF 到底在考什么

题目允许使用模型厂商的 API 客户端和原生 tool calling，但明确禁止：

- 在现成 Agent 产品上封装界面；
- 使用 LangChain、LlamaIndex、OpenAI Agents SDK、Claude Agent SDK、AutoGen、CrewAI 等 Agent 框架；
- 使用 API 服务端托管的代码执行或文件工具。

同时明确要求重要逻辑自行编写，至少包括：

1. 对话历史与上下文管理；
2. 工具定义与本地执行；
3. 模型输出解析；
4. 循环终止条件；
5. 错误处理。

面试重点不是让你背类名，而是看你能不能解释：**这五部分怎样组成闭环，以及为什么采用当前设计。**

## 2. 为什么使用 OpenAI 官方客户端仍然合规

当前项目通过 OpenAI 兼容客户端访问 DeepSeek，但客户端只承担：

- 发送 HTTP 请求；
- 设置请求超时；
- 把响应 JSON 转成 SDK 对象。

客户端没有承担：

- 消息历史维护；
- 工具参数校验；
- 本地文件和命令执行；
- 多轮循环；
- 权限审批；
- 错误重试决策；
- 预算与终止判断。

这些都由项目自己的代码实现。因此它是“模型 API 传输库”，不是 Agent 框架。

可以用一个判断方法回答评委：

> 如果把 DeepSeek 适配器换成一个假模型，项目是否仍然能够完整测试搜索、读取、修改、运行测试、回填结果和终止的循环？当前答案是可以，所以 Agent 核心不依赖某个 Agent SDK。

## 3. 考核点一：对话历史与上下文管理

### 3.1 题目为什么要求自己管理上下文

大模型接口本身通常是无状态的。所谓“下一轮还记得上一轮”，本质是调用方把需要的历史再次发送给模型。

如果没有上下文管理，模型完成第一次 `read_file` 后，下一轮就不知道：

- 用户原来要做什么；
- 自己刚才调用了哪个工具；
- 工具返回了什么；
- 文件是否已经修改；
- 测试是否已经执行。

所以消息历史是 Agent 的工作记忆，也是闭环能够持续的基础。

### 3.2 当前项目管理两种历史

#### 跨运行的可见历史

只包含用户和助手最终可见的正文，不包含：

- 隐藏推理；
- 原始工具调用；
- 完整工具结果；
- API 请求对象。

这些历史被包装成普通用户资料，并应用条数、单条字符数和总字符数限制。超出预算时保留最近的完整后缀，而不是从消息中间随意切断。

#### 单次运行内的协议历史

当前任务运行期间会完整维护：

```text
system → user → assistant(tool_calls) → tool → assistant(tool_calls) → tool → ...
```

每个工具调用必须有同 ID 的工具结果，下一轮模型才能理解执行事实并满足 tool calling 协议。

### 3.3 记忆怎样进入上下文

长期记忆是用户确认的参考资料，不是高优先级指令：

- 按工作区隔离；
- 每次运行使用开始时冻结的快照；
- 最多 32 条、合计最多 32,000 字符、单条最多 4,000 字符；
- 与当前任务一起放进普通用户数据；
- 当前任务固定放在最后；
- 系统提示明确要求重新根据当前工作区验证记忆中的说法。

### 3.4 为什么不把记忆放到 system prompt

system prompt 是高优先级策略。如果把可编辑记忆放进去，一条错误记忆可能覆盖安全规则、权限或当前任务。

当前设计把记忆当作不可信资料，意味着模型可以参考，但不能用它绕过：

- 当前任务；
- 工作区边界；
- 审批要求；
- 预算；
- 系统安全规则。

### 3.5 为什么不保留无限历史

无限历史会带来：

- 上下文超过模型限制；
- 请求成本持续增长；
- 旧任务噪声干扰新任务；
- 大工具输出淹没真正相关的信息。

当前项目通过历史条数/字符数、记忆预算、工具输出上限和运行预算控制规模。首版没有使用模型自动摘要，因为摘要可能丢失关键约束，还会引入新的模型调用和不可验证误差。

### 3.6 评委可能追问

**问：大模型不是自己有上下文吗？**

答：单次请求内部有上下文窗口，但 API 不替应用保存完整会话状态。项目必须在每轮重新提交需要的消息，并决定哪些历史允许进入。

**问：为什么旧历史不直接按 user/assistant 原角色重放？**

答：当前项目把跨运行历史视为不可信参考资料，包装成一段 user JSON；只有本次运行产生的 tool calling 历史按协议角色精确回放。这样可以避免旧助手文本在新任务里被误当成当前权威指令。

**问：模型会自己记住长期偏好吗？**

答：不会。长期记忆是项目选择并再次发送给模型的文本快照。模型没有保存记忆工具，保存必须由用户明确确认。

## 4. 考核点二：工具定义与本地执行

### 4.1 工具为什么是 Agent 的关键

普通聊天模型只能生成文本。编程 Agent 必须把“想做什么”转换成“本地真实发生什么”。

tool calling 只提供一种结构化表达：

```text
我要调用 read_file，参数是 {"path":"a.py"}
```

它不代表模型已经读到了文件。项目还必须：

1. 检查工具名；
2. 解析 JSON；
3. 检查字段和类型；
4. 判断权限与路径；
5. 在本机执行；
6. 把结果转换成模型能理解的 JSON。

### 4.2 当前六个工具为什么这样划分

| 工具 | 解决的问题 | 设计理由 |
|---|---|---|
| `list_files` | 了解仓库结构 | 比盲目读取全部文件更节省上下文 |
| `read_file` | 获取源码事实 | 分段、有字符上限，并返回文件哈希 |
| `search_text` | 定位符号和引用 | 不依赖 shell，搜索范围和输出可控 |
| `write_file` | 创建新文件 | create-only，防止模型用“写入”意外覆盖已有文件 |
| `replace_text` | 修改已有文件 | 唯一匹配 + 最近读取哈希，降低错改和并发覆盖 |
| `run_command` | 运行测试和检查 | 使用结构化 argv、风险分类、超时和输出限长 |

### 4.3 为什么 `write_file` 和 `replace_text` 不合成一个万能工具

新建和修改的风险不同：

- 新建文件最重要的是“目标出现了就失败”，不能静默覆盖；
- 修改文件最重要的是“模型修改的是自己刚读到的版本”，所以需要 SHA-256；
- 文本替换还要求旧文本恰好匹配一次，避免一次请求误改多个位置。

分开以后合同更清晰，也更容易测试每种副作用。

### 4.4 为什么文件工具只接受相对路径

相对路径始终从冻结的工作区根目录解释。项目会拒绝绝对路径、父目录穿越、Windows 设备名、ADS、受保护目录和逃逸工作区的链接。

这不是单纯的参数美化，而是让模型的文件能力具有明确边界。如果模型传入 `../../secret.txt`，工具层会返回结构化错误，而不会让文件系统自己决定结果。

### 4.5 `run_command` 为什么不用命令字符串

当前工具要求：

```json
{"argv":["python","-m","pytest","-q"],"cwd":".","timeout_seconds":120}
```

而不是：

```text
python -m pytest -q && 删除某文件
```

使用 argv 数组并设置 `shell=False` 可以避免管道、重定向、变量展开和命令拼接由 shell 隐式解释。之后再做命令分类：

- `ALLOW`：固定测试、编译和部分只读检查；
- `CONFIRM`：未知但不属于硬拒绝的可执行操作；
- `DENY`：shell 宿主、提权、危险系统命令、远端或历史修改型 Git 操作。

### 4.6 为什么命令输出也要有边界

一个错误命令可能打印数百 MB 日志。如果先全部读进内存再截断，会同时伤害：

- Agent 进程内存；
- 模型上下文；
- API 成本。

当前实现并行排空 stdout/stderr，并只保留有界头尾及总字节统计。模型既能看到关键错误，又不会被无限输出拖垮。

### 4.7 评委可能追问

**问：工具 Schema 已经声明了类型，为什么还要本地校验？**

答：Schema 是给模型的生成提示，不是安全边界。模型可能生成未知字段、错误类型、非法路径或不完整 JSON，本地执行前必须再次验证。

**问：为什么不用 DeepSeek 或 OpenAI 的托管文件工具？**

答：PDF 明确禁止依赖 API 服务端托管的代码执行或文件工具。当前六个工具都是本项目在本机实现和执行的。

**问：命令返回非零是不是 Agent 失败？**

答：通常不是。它是一次工具观察结果，模型可以根据 stdout/stderr 修复问题。只有运行级错误才终止整个 Agent。

## 5. 考核点三：模型输出解析

### 5.1 为什么不能直接相信 SDK 对象

模型输出可能存在：

- `finish_reason` 与消息内容矛盾；
- tool call 缺少 ID 或函数名；
- 参数不是字符串或不是 JSON object；
- 一次返回多个 choice；
- `length` 时留下半截工具参数；
- Token 用量字段异常。

如果直接把这些内容写入历史或执行，可能产生协议损坏或错误副作用。

### 5.2 当前项目的两层解析

#### 供应商适配层

把 DeepSeek/OpenAI SDK 对象规范化成项目自己的不可变类型：

- `AssistantMessage`
- `ToolCall`
- `TokenUsage`
- `ModelCompletion`

适配层解决“供应商数据长什么样”。

#### Agent 控制层

根据 `finish_reason` 和组合关系决定：

- 是否允许消息进入历史；
- 是否执行工具；
- 是否重试同一个请求；
- 是否结束运行。

控制层解决“这个响应意味着什么”。

### 5.3 为什么被截断响应绝不能执行

假设模型生成：

```json
{"path":"a.py","old_text":"...","new_text":"...
```

此时即使 SDK 恰好暴露了部分 tool call，也不能猜测剩余参数。当前项目对 `length` 直接以 `truncated_response` 结束，并且不把部分 assistant 消息写入历史。

原则是：

> 没有完整通过协议检查的模型意图，不能触发本地副作用。

### 5.4 为什么工具参数使用严格 JSON

参数必须：

- 是一个 object，不是数组或标量；
- 没有重复键；
- 没有 `NaN`、`Infinity`；
- 只包含该工具允许的字段；
- 字段类型和长度正确。

这让模型输出从“自然语言建议”变成“可验证的执行合同”。

### 5.5 评委可能追问

**问：`finish_reason=stop` 就一定结束吗？**

答：还要确认没有 tool calls，并且 `content` 是非空文本。字段组合冲突会被判为协议错误。

**问：为什么保留 `reasoning_content`？**

答：DeepSeek thinking + tools 的连续调用要求工具轮次回传推理字段。项目只在当前运行内保留用于协议回放，不展示、不持久化、不写诊断日志。

## 6. 考核点四：循环终止条件

### 6.1 为什么不能只相信模型会停止

模型可能：

- 反复读取同一个文件；
- 重复运行失败命令；
- 不断尝试新的修改；
- 遇到服务端资源问题持续重试。

如果没有程序级预算，Agent 可能无限消耗时间和 API 费用。

### 6.2 当前终止条件

#### 正常终止

- 模型返回合法、非空 final：`model_finished / model_final`。

#### 预算终止

- 模型调用达到上限；
- 工具调用达到上限；
- 累计 Token 超出上限；
- 总墙钟时间耗尽。

#### 失败终止

- API 致命错误；
- 内容过滤；
- 模型响应截断；
- 协议冲突；
- 内部不变量破坏。

#### 外部终止

- 用户取消。

### 6.3 为什么同时需要多种预算

单一预算无法覆盖所有失控方式：

| 预算 | 防止什么 |
|---|---|
| 模型次数 | 许多小请求形成无限循环 |
| 工具次数 | 一次模型返回大量工具调用 |
| Token | 少量但极大的请求/响应导致成本失控 |
| 总时间 | 网络等待、命令挂起、审批等待拖住运行 |
| 单次 API/命令超时 | 单个操作占满全部运行时间 |

### 6.4 为什么重复检测只警告、不作为终止原因

相同工具参数和结果可以证明“交换相同”，但不能证明“整个任务毫无语义进展”。例如模型可能在比较不同假设时再次确认同一文件。

所以当前策略是：

- 第三次相同交换开始提醒模型改变策略；
- 不改变原工具结果；
- 不自行压制调用；
- 仍由硬预算保证最终停止。

这是保守、可解释的启发式，而不是冒充通用规划器。

### 6.5 评委可能追问

**问：模型说“完成了”，为什么还不算验证成功？**

答：模型 final 只是控制协议的正常停止。任务正确性应由测试、静态检查或 Agent 看不到的独立 verifier 判断，不能让被评估者自己宣布通过。

## 7. 考核点五：错误处理

### 7.1 当前错误分层

| 层级 | 示例 | 处理方式 |
|---|---|---|
| 工具输入错误 | 非法 JSON、未知字段、路径不存在 | 结构化回填，让模型自纠 |
| 工具执行错误 | 测试非零、超时、文件哈希过期 | 结构化回填，通常继续循环 |
| 权限错误 | 需要审批、用户拒绝、硬拒绝命令 | 回填明确错误码，不伪装成执行成功 |
| API 瞬时错误 | 连接失败、超时、429、500、503 | 在剩余预算内指数退避重试 |
| API 致命错误 | 认证、参数或其他不可重试错误 | 结束运行 |
| 模型协议错误 | tool call ID 重复、reason 冲突 | 不执行副作用，结束运行 |
| 运行控制错误 | 取消、总时间或次数耗尽 | 统一终态结束 |
| 诊断错误 | trace 写入失败 | 忽略，不改变 Agent 结果 |

### 7.2 为什么关闭 SDK 自动重试

如果 SDK 内部重试，Agent 控制器可能不知道真实请求了几次、耗时多久，也无法把重试纳入总预算。

当前项目把 SDK 自动重试设为 0，由 Agent 自己控制：

- 哪些错误可以重试；
- 最多重试多少次；
- 每次是否仍有剩余时间；
- 指数退避和 jitter；
- 每次尝试是否计入模型调用预算。

### 7.3 为什么不自动重试有副作用工具

模型 API 请求在历史不变时可以安全地原样重试；文件写入或命令执行却可能已经部分产生效果。

因此控制器不会看到工具异常就盲目重试。它把结果交给模型，由模型基于新状态决定下一步，避免重复副作用。

### 7.4 同一轮一个工具失败，后面的工具怎么办

普通工具失败不会取消同批次后续工具。控制器仍为每个调用 ID 生成一个结果，以保持协议完整。

只有以下全局条件会让剩余调用得到取消结果并在批次结束后终止：

- 用户取消；
- 总墙钟预算耗尽；
- 运行进入不可继续的终止状态。

### 7.5 评委可能追问

**问：为什么不是遇到任何异常都停止？**

答：编程过程天然包含失败测试、错误路径和参数修正。如果全部视为运行失败，Agent 就不能自主纠错。项目只让模型无法修复的运行级错误终止。

**问：为什么 trace 失败不让任务失败？**

答：诊断记录是旁路能力，不是任务正确性的组成部分。它出错不应改变文件修改和测试结果，否则观察系统会反过来控制业务语义。

## 8. PDF 凭据规则在运行时如何落实

PDF 要求 API key 不得进入仓库、README 或视频。当前运行时进一步做了：

- key 从环境变量或未入库配置读取；
- key 不进入模型消息历史；
- `.env`、私钥和证书等文件受到文件工具保护；
- 子进程使用最小环境变量白名单，主动剥离 API key、Token 和数据库凭据；
- 诊断事件使用字段白名单，不记录请求头、完整工具输出或隐藏推理。

仍要诚实说明：这些措施降低误泄漏风险，但获准执行的任意程序仍具有当前系统用户权限，项目没有实现 OS 级强沙箱。

## 9. 用一句话对应五项要求

| PDF 要求 | 当前项目的一句话回答 |
|---|---|
| 上下文管理 | 自己构建有界历史、记忆和当前任务，并维护完整工具回合 |
| 工具定义与执行 | 自己声明六个 Schema，在本机校验权限和参数后执行 |
| 模型输出解析 | 先规范化供应商响应，再按 finish reason 和协议组合决策 |
| 循环终止 | 正常 final、预算、取消、协议和 API 错误都有明确终态 |
| 错误处理 | 可纠正错误回填模型，运行级错误才终止，瞬时 API 错误有界重试 |
