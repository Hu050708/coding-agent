# 01 - 一次智能体运行到底发生了什么

## 1. 最小心智模型

可以把当前 Agent 理解为一个“模型驱动、程序控制”的反馈循环：

```text
用户任务
   ↓
构造上下文和工具说明
   ↓
调用 DeepSeek ───────────────┐
   ↓                         │
模型返回 final 或 tool_calls │
   ↓                         │
解析并检查模型输出           │
   ↓                         │
本地执行工具                 │
   ↓                         │
把工具事实结果加入历史 ──────┘
   ↓
满足终止条件后返回运行结果
```

它之所以能完成多步任务，不是因为一次模型请求解决了一切，而是因为工具结果会成为下一轮模型决策的新证据。

例如修复一个加法函数时，模型可能依次经历：

```text
搜索函数 → 读取文件 → 修改文件 → 运行测试 → 根据测试结果决定是否继续 → 最终回答
```

每个箭头通常对应一次新的模型决策。

## 2. 运行开始前冻结什么

一次运行不是只有一句用户问题。开始前会形成一份不可变的运行输入：

- 工作区：本次允许文件工具访问的目录；
- 当前任务：用户这次真正要求完成的事情；
- 权限模式：询问、Agent 或工作区完全访问；
- 可见历史：之前用户和助手能看到的消息；
- 记忆快照：用户确认过、且本次允许使用的工作区记忆；
- 预算：最大模型次数、工具次数、Token 和总时间。

这里强调“冻结”，因为运行中途随意改变权限或记忆会导致行为不可复现。评委如果问“为什么运行开始后改权限不立即影响旧任务”，答案就是：权限本身是本次运行的输入，运行途中漂移会让同一个任务前后使用两套规则。

## 3. 初始消息如何组成

控制器不会把所有数据都提升成系统指令。当前运行的消息大致分三层：

1. **系统消息**：声明这是本地编程 Agent，要求先检查、最小修改、验证结果，并把仓库内容视为不可信数据。
2. **历史资料**：旧的可见消息被包装成一段普通用户 JSON 资料，而不是重新伪装成新的系统规则。
3. **当前任务**：如果有长期记忆，记忆和任务放在同一段结构化用户数据中，当前任务固定放在最后；没有记忆就直接发送任务原文。

这么设计有两个目的：

- 系统规则的优先级不会被历史或记忆覆盖；
- 当前任务在结构和位置上都比参考资料更明确。

### 会话历史和长期记忆的区别

| 对比项 | 会话历史 | 工作区记忆 |
|---|---|---|
| 来源 | 同一会话以前的用户/助手可见消息 | 用户明确保存或确认的工作区知识 |
| 共享范围 | 当前会话 | 同一工作区的不同会话 |
| 主要用途 | 保持对话连续性 | 保存稳定约定、事实或决策 |
| 模型能否自动写入 | 不能 | 不能 |
| 本次运行是否变化 | 开始前形成有界快照 | 开始前形成有界快照 |

模型没有“保存长期记忆”工具。这样可以避免模型把误解、临时猜测或仓库中的提示注入内容悄悄写成永久事实。

## 4. 每一轮模型调用

进入主循环后，一轮模型调用可以拆成八步。

### 第一步：检查全局停止条件

在发请求前先检查：

- 用户是否取消；
- 总墙钟时间是否耗尽；
- 模型调用次数是否到达上限；
- 已观察到的累计 Token 是否到达上限。

这些判断属于控制器，而不是依赖模型“自觉停止”。

### 第二步：把完整运行历史和工具 Schema 发给模型

当前实现使用非流式 DeepSeek Chat Completions，请求中包含：

- 当前运行积累的全部消息；
- 八个函数工具的 JSON Schema；
- thinking 高强度配置；
- 单次输出 Token 上限；
- 不超过剩余总时间的请求超时。

官方 OpenAI 客户端这里只负责 HTTP 和响应对象。它没有维护 Agent 循环，也没有在服务端替项目执行工具。

### 第三步：适配器规范化供应商响应

DeepSeek 的 SDK 对象会先被转换成项目自己的 `ModelCompletion`：

- `finish_reason`：模型为什么停止本轮生成；
- `content`：普通回答；
- `reasoning_content`：thinking 模式的推理状态；
- `tool_calls`：函数名、调用 ID 和原始 JSON 参数；
- `usage`：本轮 Token 用量。

供应商适配器只做传输和格式转换，不决定是否执行工具。真正的决策仍在 Agent 控制器。

### 第四步：根据 `finish_reason` 分类

| `finish_reason` | 控制器行为 |
|---|---|
| `tool_calls` | 校验调用结构，执行工具，继续下一轮 |
| `stop` | 只有在没有工具调用且正文非空时，作为正常 final 结束 |
| `length` | 认为响应被截断，不执行可能只生成一半的工具参数 |
| `content_filter` | 明确失败，不把不完整消息加入历史 |
| `insufficient_system_resource` | 丢弃这次未完成消息，在预算内原请求重试 |
| 未知值或字段冲突 | 以协议错误结束 |

关键思想是：**先完整校验，再把消息提交到历史或执行副作用。**

### 第五步：校验工具调用批次

如果模型一次返回多个工具调用，控制器会在执行前整体检查：

- 调用列表不能为空；
- 每个调用 ID 在整个运行中唯一；
- 整批调用不能超过剩余工具预算。

随后，每个调用在轮到自己执行时，还必须把参数解析成严格 JSON 对象。参数不合法的调用会得到错误结果，不会触发本地副作用，也不会破坏其他调用的结果配对。

调用 ID 很重要，因为 OpenAI 兼容协议要求每个 assistant tool call 后面恰好有一个同 ID 的 `role=tool` 结果。

### 第六步：按顺序执行工具

当前项目不并行执行同一轮的多个工具，而是严格按模型给出的顺序处理。原因包括：

- 两个修改可能操作同一个文件；
- 后一个工具可能依赖前一个工具产生的状态；
- 顺序执行更容易复现、记录和解释；
- 文件哈希可以让过期修改明确失败，而不是产生不确定覆盖。

工具调用会经过三层：

```text
模型参数
  → 工具参数合同
  → 权限与工作区策略
  → 本地工具实现
```

### 第七步：把成功或失败结果回填

工具成功统一返回：

```json
{"ok":true,"data":{},"meta":{}}
```

工具失败统一返回：

```json
{"ok":false,"error":{"code":"...","message":"...","retryable":false}}
```

失败结果通常不会直接终止 Agent。例如测试退出码为 1，会成为 `command_exit_nonzero` 工具结果。模型看到 stderr 后可以修改代码，再次运行测试。

这解释了你之前看到很多 `run_command 失败` 但任务最后完成的现象：那些“失败”通常是编程过程中的测试失败或命令退出非零，而不是 Agent 控制器崩溃。

### 第八步：带着新事实进入下一轮

控制器依次把以下消息加入本次运行历史：

1. 模型产生的完整 assistant tool turn；
2. 每个工具调用对应的 tool result。

下一次请求模型时，模型能看到“自己刚才要求做什么”和“本地真实发生了什么”，于是形成闭环。

## 5. thinking 内容为什么保留但不展示

DeepSeek thinking + tools 协议要求工具轮次中的 `reasoning_content` 在下一轮请求中一起回传，否则可能破坏供应商协议。因此项目在**本次运行的内存历史**中保留它。

但它不会：

- 展示给用户；
- 写入可见会话历史；
- 写入诊断事件；
- 作为长期记忆保存。

这同时满足协议连续性和最小数据保留。

## 6. 工具失败后为什么还能继续

错误分两类：

### 模型可以纠正的错误

例如：

- 文件不存在；
- 旧文本没有唯一匹配；
- 文件哈希已经过期；
- 测试退出非零；
- 参数字段错误；
- 命令被策略拒绝。

这些错误会作为工具结果回填，让模型改变路径、重读文件、修改参数或换一种验证方式。

### 模型无法纠正的运行级错误

例如：

- 供应商响应违反基本协议；
- API 密钥或权限错误；
- 总预算耗尽；
- 用户取消；
- 控制器内部不变量破坏。

这些会结束整个运行。

判断原则是：

> 能通过下一次模型决策修复的问题，作为观察结果回填；无法通过下一步行动修复的问题，才结束 Agent。

## 7. 当前八个本地工具

| 工具 | 作用 | 关键约束 |
|---|---|---|
| `list_files` | 查看目录结构 | 有条目上限、稳定排序、不跟随目录链接 |
| `read_file` | 分段读取文本 | 只读 UTF-8 文本，返回哈希和截断信息 |
| `search_text` | 在工作区搜索字面文本 | 不经过 shell，限制文件数、字节数和结果量 |
| `make_directory` | 创建目录结构 | 幂等创建，可创建父目录，不跟随任一路径链接 |
| `write_file` | 新建文件 | 只创建，不覆盖已有文件，原子发布 |
| `replace_text` | 修改已有文本 | 旧文本必须唯一匹配，并携带最近读取的 SHA-256 |
| `delete_file` | 删除普通文件 | 最近读取哈希必须匹配，不删除目录或链接，默认需要审批 |
| `run_command` | 执行测试或检查命令 | `argv` 数组、`shell=False`、工作区 cwd、风险分类、超时和输出限长 |

模型厂商只看到这些工具的 Schema。实际文件和命令操作都由本项目的本地 Python 代码完成，符合 PDF 对“不得依赖服务端托管代码执行或文件工具”的要求。

## 8. 一次典型修复任务的消息变化

假设任务是“修复 `add()` 并运行测试”。简化后的历史会这样增长：

```text
system: 运行规则
user: 当前任务

assistant: tool_calls(search_text)
tool: 搜索到 mathutil.py:1

assistant: tool_calls(read_file)
tool: 返回源码和 SHA-256

assistant: tool_calls(replace_text)
tool: 修改成功，返回新哈希

assistant: tool_calls(run_command)
tool: pytest exit_code=0

assistant: 已修复并通过测试
```

如果 pytest 返回 1，历史不会结束在错误处，而是继续：

```text
tool: ok=false, code=command_exit_nonzero, stderr=...
assistant: 根据失败信息再次读取或修改
```

## 9. 如何看懂运行事件

运行过程会发布一组结构化事件。它们是对 Agent 状态机的观察，不是另一套执行逻辑：

| 事件 | 表示什么 |
|---|---|
| `run.accepted` | 任务已经登记，等待工作线程处理 |
| `run.started` | Agent 正式开始运行 |
| `memory.loaded` | 本次记忆快照已加载、为空、禁用或不可用 |
| `model.completed` | 模型完成了一次决策，可能是 `tool_calls` 或 `stop` |
| `tool.started` | 一个本地工具开始执行 |
| `tool.completed` | 工具已经得到成功或失败的结构化结果 |
| `approval.required` | 权限策略要求暂停并等待用户决定 |
| `approval.resolved` | 审批被批准、拒绝、取消或过期 |
| `run.finished` | 控制器进入最终状态，不再发起新动作 |

因此日志中的“模型完成一次决策 / tool_calls”不是异常，它表示模型决定先操作工具，而不是立即回答。

## 10. 状态和终止原因不要混淆

顶层状态只有四类：

| 状态 | 含义 |
|---|---|
| `model_finished` | 模型正常给出非空 final |
| `failed` | API、协议或内部错误导致失败 |
| `cancelled` | 用户取消 |
| `budget_exhausted` | 次数、Token 或时间预算耗尽 |

终止原因则更具体：

- `model_final`
- `max_model_calls`
- `max_tool_calls`
- `token_budget_exceeded`
- `wall_time_exceeded`
- `api_fatal_error`
- `content_filtered`
- `truncated_response`
- `protocol_error`
- `user_cancelled`
- `internal_invariant_violation`

### 最重要的区别

`model_finished/model_final` 只表示模型选择停止调用工具，并给出了最终文本。它不证明测试真的通过，更不证明隐藏需求全部满足。

项目正式演示通过真实测试和 Agent 工作区外的独立 verifier 验收，正是为了避免把模型的自我声明当成事实。

## 11. 当前默认预算

当前源码默认值如下，实际运行可以由配置覆盖：

| 预算 | 默认值 |
|---|---:|
| 最大模型调用 | 50 次 |
| 最大工具调用 | 100 次 |
| 累计 Token | 1,000,000 |
| 总墙钟时间 | 600 秒 |
| 单次 API 等待 | 60 秒 |
| 瞬时 API 重试 | 最多追加 3 次 |
| 单次模型最大输出 | 8192 Token |

每次 API 或工具等待的实际时间都会被“操作自身上限”和“本次运行剩余总时间”中的较小值限制。

## 12. 完全重复调用如何处理

如果同一运行中相同的：

- 工具名；
- 规范化参数；
- 去除耗时、时间戳后的结果

累计出现到第三次，控制器会在第三次工具结果的 `meta` 中加入 `progress_warning`，提醒模型不要继续机械重复。

它不会自动终止，也不会把原来的成功改成失败。原因是“工具交换完全相同”不等于“整个任务语义上毫无进展”。真正保证最终停止的仍然是硬预算。

检测器只保留最多 256 个 SHA-256 指纹，不保留原始文件内容、参数或命令输出。
