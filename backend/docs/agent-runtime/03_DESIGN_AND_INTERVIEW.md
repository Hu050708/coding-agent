# 03 - 设计辩护、能力边界与面试问答

## 1. 什么叫“为设计决策辩护”

不是说“这样写更好”，而是要说明四件事：

1. 当时要解决什么具体问题；
2. 当前方案怎样解决；
3. 为什么没有选择另一个看似更高级的方案；
4. 当前方案还有什么真实边界。

推荐使用下面的答题句式：

> 我需要解决 A。当前选择 B，因为它在首版中能保证 C，并且可以通过 D 测试。代价是 E；如果后续有 F 数据或需求，我会再升级为 G。

例如：

> 我需要避免模型机械重复。当前只对完全相同的工具交换做指纹检测并提示，因为这种事实可以稳定测量；但完全相同不等于任务一定无进展，所以我没有直接终止。最终停止仍由次数、Token 和时间硬预算保证。

## 2. 当前项目最重要的设计取舍

## 2.1 为什么核心采用显式循环，而不是 Agent 框架

题目本身要求重要逻辑自行实现。显式循环让以下行为都可以看见和测试：

- 每轮到底发了哪些消息；
- 工具什么时候执行；
- 哪个错误会回填、重试或终止；
- 每个工具调用如何配对结果；
- 预算在什么位置扣除；
- 最终状态为什么产生。

如果用 Agent 框架，这些关键行为可能隐藏在框架内部，既违反题意，也难以在面试中证明自己理解。

## 2.2 为什么模型适配器和 Agent 控制器分开

模型适配器只处理 DeepSeek 请求/响应格式，Agent 控制器只依赖统一的完成结果。

好处：

- 假模型可以离线驱动完整循环；
- 供应商字段变化不会扩散到工具层；
- API 错误和协议错误能明确区分；
- 将来换模型时不用重写工具和状态机。

这叫依赖倒置，但面试时不必只背术语。直接说“把网络传输和 Agent 决策拆开，才能独立测试循环”更清楚。

## 2.3 为什么模型请求使用非流式

当前 DeepSeek 请求设置 `stream=False`。理由不是不会做流式，而是首版优先保证 tool calling 协议正确：

- 流式工具调用需要拼接增量 ID、函数名和 JSON 参数；
- thinking 内容和多个 tool call 的增量顺序更复杂；
- 中途断流会产生“参数是否完整”的新状态；
- 非流式响应可以先完整验证，再执行副作用。

代价是用户看不到模型逐字输出，首字延迟更高。当前项目把“可靠完成本地编程闭环”放在“文字实时出现”之前。

## 2.4 为什么多工具顺序执行

同一轮的工具可能互相依赖，也可能修改同一文件。顺序执行提供：

- 确定的副作用顺序；
- 确定的消息回填顺序；
- 更容易复现的问题；
- 与 SHA-256 乐观锁配合的清晰冲突语义。

代价是只读工具无法并行提速。首版可靠性和可解释性高于吞吐量。如果以后并行，只应先并行无副作用、输入互不依赖的只读工具，并显式声明依赖图。

## 2.5 为什么修改文件需要最近读取的 SHA-256

模型读取文件后，到实际修改前，文件可能被别的程序或更早的工具改过。

`replace_text` 要求模型提供读取结果中的哈希，并在写入前再次比对：

- 相同：说明模型至少基于当前已知版本修改；
- 不同：返回 `stale_file`，要求重新读取。

这是乐观并发控制。它降低陈旧写覆盖风险，但不能夸大成绝对原子 CAS；通用文件系统仍可能存在非常短的检查与替换竞态窗口。

## 2.6 为什么原生实现 `search_text`

仅靠 `list_files + read_file` 也能搜索，但会浪费模型轮次和上下文。让模型通过命令调用 `rg`，又会把普通代码定位变成命令审批问题。

所以项目提供有界的本地字面搜索：

- 不依赖 shell；
- 复用工作区和受保护路径规则；
- 文件数、总字节、单文件和输出都有上限；
- 稳定排序，结果容易复现。

首版不用正则，是因为大多数符号定位可由字面搜索满足，而正则会增加转义错误和性能风险。

## 2.7 为什么重复检测只给建议

检测器判断的是“工具名 + 规范化参数 + 去除时间字段后的结果”是否完全相同。这只能说明一次交换重复，不能证明整个任务没有进展。

因此它：

- 同一运行中累计第三次时加入提示；
- 保留原 `ok` 和错误码；
- 不阻止工具执行；
- 不新增终止原因；
- 用最多 256 个哈希控制自身内存。

这是一个低风险恢复提示，不是假装理解任务计划。

## 2.8 为什么模型不能自动保存长期记忆

模型可能把以下内容误写为永久事实：

- 一次测试中的临时现象；
- 自己的错误推断；
- 恶意仓库中的提示注入；
- 只对当前分支有效的约定。

所以当前记忆必须由用户明确确认，模型只读。记忆在运行中作为普通参考资料，并要求根据当前工作区重新验证。

代价是自动化程度较低，但长期状态更可控、更容易解释和删除。

## 2.9 为什么暂时不用向量检索

当前工作区记忆规模小、由用户选择、具有明确的条数和字符预算。确定性的置顶/顺序选择比引入 embedding 更容易复现。

使用 pgvector 镜像不等于项目已经使用向量记忆。真正引入 RAG 还需要明确：

- embedding 模型和版本；
- 切分方式；
- 相似度阈值；
- 召回失败的行为；
- 如何解释某条记忆为什么进入上下文。

首版没有这些必要需求，所以不为了“看起来高级”而增加不可解释组件。

## 3. 三档权限应该怎样理解

权限是一次运行冻结的应用策略，不是前端标签。

| 模式 | 文件读取/搜索 | 目录/文件新建与修改 | 文件删除 | 普通低风险命令 | 需要确认的命令 | 硬拒绝命令 |
|---|---|---|---|---|---|---|
| `ask` 请求批准 | 自动 | 每次确认 | 每次确认 | 每次确认 | 每次确认 | 拒绝 |
| `agent` 帮我批准 | 自动 | 工作区内自动 | 请求确认 | 自动 | 请求确认 | 拒绝 |
| `workspace_full` 工作区完全访问 | 自动 | 工作区内自动 | 工作区内自动 | 自动 | 自动 | 拒绝 |

### 3.1 为什么权限要按运行冻结

如果运行到一半根据界面最新值改变权限，前半段和后半段会使用不同安全合同：

- 无法解释某个动作为什么当时被允许；
- 同一任务无法复现；
- 用户可能误以为改的是下一次任务，实际影响当前任务。

冻结后，每次运行都能明确回答：“这次任务在什么能力边界内执行？”

### 3.2 三档权限都不能绕过什么

无论选择哪一档，都不能绕过：

- 工作区文件边界；
- 受保护文件规则；
- 工具参数合同；
- 命令分类中的 `DENY`；
- 模型、工具、Token 和时间预算；
- 用户取消；
- 文件哈希冲突。

当策略要求确认时，工具线程会暂停等待一次明确决定。等待存在审批超时，也受本次运行剩余总时间和取消信号约束；过期、拒绝或取消都会形成工具失败结果，而不是默认为批准。

### 3.3 为什么“工作区完全访问”仍不是沙箱

文件工具可以严格限制自身只操作工作区。但一旦允许执行 Python、Node 或其他程序，该程序本身仍拥有当前 Windows 用户权限，理论上可能访问工作区外文件或网络。

`shell=False`、最小环境变量、cwd 和命令分类只能降低风险。真正强隔离需要：

- 容器；
- 虚拟机；
- 受限系统账户；
- 操作系统级沙箱策略。

当前项目没有实现这些能力，答辩时应主动说清楚。

## 4. 如何证明 Agent 不是“模型自说自话”

当前项目有三层证据：

### 第一层：假模型状态机测试

不调用 DeepSeek，由预设模型响应驱动真实工具，验证：

```text
search → read → replace → pytest → final
```

这证明循环、消息配对和本地工具不是靠线上模型碰巧完成。

### 第二层：协议和边界测试

测试覆盖：

- finish reason 决策表；
- 重复 tool call ID；
- 非法 JSON；
- 工具失败后的继续执行；
- 路径逃逸；
- 受保护文件；
- 命令审批、超时和取消；
- 环境变量剥离；
- 各种预算终止。

### 第三层：真实任务与独立验收

真实模型完成任务后，再由 Agent 工作区之外的 verifier 检查结果。Agent 无法修改验收程序，因此比“模型 final 说完成了”更可信。

## 5. 高频面试问答

### 5.1 “你的项目为什么算 Agent，而不是普通聊天机器人？”

因为它不是一次问答。模型能提出结构化工具调用，项目在本地执行并把结果反馈，模型基于新事实继续决策，直到正常 final 或控制器终止。这形成了感知、行动、反馈的多轮闭环。

### 5.2 “整个系统里谁真正控制 Agent？”

模型控制任务策略，程序控制执行边界。模型决定“想调用什么”，控制器决定“格式是否有效、是否允许、是否执行、结果是什么、是否继续”。最终终止权在控制器。

### 5.3 “为什么不用 LangChain 或 Agents SDK？”

题目禁止 Agent 框架，而且核心考点正是循环、上下文、工具和错误策略。当前项目只使用底层 API 客户端传输请求，重要逻辑全部显式实现并可单测。

### 5.4 “工具调用是不是 DeepSeek 帮你执行的？”

不是。DeepSeek 只生成工具名和 JSON 参数。项目自己的 `ToolRegistry` 在本机校验并调用 Python 工具函数，模型厂商看不到本地文件系统执行权。

### 5.5 “为什么工具 Schema 不能作为安全保障？”

Schema 只帮助模型生成正确参数，模型仍可能输出错误类型、未知字段、危险路径或不完整 JSON。真正的安全边界必须在本地执行前再次校验。

### 5.6 “Agent 怎么记住上一轮工具结果？”

控制器把 assistant tool call 和对应的 `role=tool` JSON 结果加入消息历史，下一轮把完整运行历史重新发给模型。API 本身不替项目保存这段状态。

### 5.7 “为什么跨会话历史和当前工具历史处理方式不同？”

跨运行只保留用户可见正文，并作为不可信资料重新提供；当前运行必须保留精确的 assistant/tool 协议链，才能正确完成 tool calling。隐藏推理和完整工具输出不会变成永久会话历史。

### 5.8 “长期记忆和 PostgreSQL 是一回事吗？”

不是。存储系统只是载体。真正提供给模型的记忆，是从已确认记忆中选择并冻结的有界文本集合。会话、运行、事件和审批等数据不都属于模型记忆。

### 5.9 “为什么记忆要冻结？”

保证这次运行始终看到同一组输入，并能事后解释模型当时使用了哪些记忆。否则运行中修改记忆会让前后决策依据不一致。

### 5.10 “模型生成错误 JSON 怎么办？”

严格解析失败后生成 `invalid_arguments` 工具结果，不执行本地副作用。只要运行级预算仍允许，模型下一轮可以修正参数。

### 5.11 “一个工具失败，会不会整次任务立即失败？”

通常不会。文件不存在、测试非零等属于模型可纠正的观察结果，会回填历史。只有协议错误、API 致命错误、取消或预算耗尽等运行级问题才终止。

### 5.12 “为什么同一轮后面的工具还会执行？”

普通工具失败不一定让其他调用失去意义，而且协议要求每个 call ID 有结果。当前实现继续顺序处理；只有取消或总时间耗尽等全局条件才取消剩余调用。

### 5.13 “为什么模型调用失败可以自动重试，工具失败却不盲目重试？”

历史不变的 API 请求通常可以原样重试；有副作用工具可能已经部分改变本地状态。自动重做写入或命令可能放大副作用，所以工具结果应交给模型重新决策。

### 5.14 “API 重试为什么由你自己管理？”

为了把每次尝试计入模型次数和总时间，并统一判断可重试错误。SDK 自动重试被关闭，避免内部发生控制器看不见的请求和等待。

### 5.15 “为什么工具调用不并发？”

并发写会引入顺序不确定和文件冲突；同一轮调用还可能有隐含依赖。首版按顺序执行，更容易复现和验证。未来可以只对明确独立的只读调用做受控并发。

### 5.16 “测试命令失败为什么页面显示 run_command 失败？”

工具层把非零退出码准确标记为 `command_exit_nonzero`。这表示这次命令事实上的退出状态，不表示 Agent 线程崩溃。模型会读取输出并继续修复。

### 5.17 “模型 final 为什么不等于任务成功？”

final 只是模型停止调用工具的协议信号。模型可能误判或没有覆盖隐藏条件。真正正确性需要测试、静态检查或独立 verifier。

### 5.18 “如果模型一直重复同一个失败命令怎么办？”

第三次相同工具交换开始收到 `progress_warning`；如果仍不改变策略，模型次数、工具次数、Token 和总时间预算最终会强制停止。

### 5.19 “为什么不在第三次重复时直接停止？”

完全相同的交换不一定等于任务语义无进展。当前证据只够支撑提醒，不足以支撑新增一个自动失败结论。硬预算已经提供确定终止。

### 5.20 “三档权限有什么本质区别？”

区别是哪些动作自动执行、哪些需要确认。`ask` 最保守；`agent` 自动完成常规工作区读写，但删除文件和风险命令仍需确认；`workspace_full` 自动执行所有非硬拒绝操作。三档都不能绕过工作区和 `DENY`。

### 5.21 “为什么权限不是越高越好？”

权限越高，人工中断越少，但误执行的影响更大。默认 `agent` 在自主性和风险之间折中：正常文件工作自动，删除文件和风险命令仍确认。

### 5.22 “为什么 `shell=False` 还不算安全沙箱？”

它只是禁止 shell 解释管道、重定向和展开。被允许的可执行程序仍有当前用户权限，可能自行访问外部文件或网络。强隔离需要 OS 层机制。

### 5.23 “为什么采用非流式模型响应？”

为了先获得完整 tool call，再校验参数和 finish reason，避免半截增量触发副作用。代价是没有逐字输出，但首版协议正确性更重要。

### 5.24 “如何防止 API key 泄漏给命令？”

命令子进程只继承最小环境白名单，主动移除 API key、Token 和数据库凭据；文件工具也禁止读取真实 `.env` 和私钥类文件。但这不是绝对沙箱，仍需使用不含敏感资料的工作区。

### 5.25 “日志能证明 Agent 绝对安全或任务绝对正确吗？”

不能。诊断事件用于解释模型次数、工具状态、耗时和终止原因，而且不保存敏感正文。它可能被本机进程修改，不是不可抵赖审计；任务正确性仍靠独立验收。

### 5.26 “这个项目最有价值的创新是什么？”

不是堆功能，而是把最小 Agent 闭环做成可解释、可恢复、有边界的系统：严格 finish reason 决策、完整工具配对、有界本地工具、三档权限、记忆快照、重复调用恢复提示，以及假模型和独立 verifier 形成的验证链。

### 5.27 “当前最大不足是什么？”

可以诚实回答：

- 命令执行不是 OS 沙箱；
- 非流式响应首字延迟较高；
- 记忆是确定性文本选择，没有语义检索；
- 工具按顺序执行，吞吐不是最优；
- 模型 final 仍需外部测试判定正确性。

这些边界是有意识的首版取舍，不应伪装成已经解决。

## 6. 面试中不要说错的十句话

| 不要这样说 | 应该这样说 |
|---|---|
| “DeepSeek 帮我读写文件” | DeepSeek 提议工具调用，本项目在本机执行 |
| “模型自己记得以前的对话” | 项目选择并重新发送有界历史 |
| “PostgreSQL 就是 Agent 记忆” | 数据库是载体，送模的有界文本快照才是记忆输入 |
| “模型说完成就说明任务成功” | final 只代表停止调用工具，还需测试或 verifier |
| “工作区完全访问就是完全控制电脑” | 它只放宽非禁止操作审批，仍有应用边界 |
| “shell=False 就绝对安全” | 它减少 shell 注入面，但不是 OS 沙箱 |
| “工具报错就会结束 Agent” | 可纠正工具错误会回填模型继续处理 |
| “重复三次就自动终止” | 第三次开始提示，硬预算负责终止 |
| “用了 OpenAI SDK 就用了 Agent SDK” | 使用的是底层 API 客户端，不是 Agent 框架 |
| “日志证明没有任何越界行为” | 日志用于诊断，不是不可抵赖安全审计 |

## 7. 一页速记

### 核心闭环

```text
模型提议 → 本地校验 → 权限决策 → 本地执行 → 结果回填 → 模型再决策
```

### PDF 五项

1. 上下文：有界可见历史 + 冻结记忆 + 当前运行完整工具历史。
2. 工具：八个自研本地工具，Schema 只描述，本地校验才是执行边界。
3. 解析：供应商响应先规范化，再按 finish reason 和字段组合决策。
4. 终止：final、模型次数、工具次数、Token、时间、取消和致命错误。
5. 错误：可纠正错误回填；API 瞬时错误有界重试；运行级错误终止。

### 三个关键设计

- 每个 tool call ID 恰好对应一个 tool result。
- 模型 final 不等于任务验证成功。
- 权限策略不是 OS 沙箱。

### 三个加分点

- 修改文件使用唯一文本匹配和 SHA-256 乐观锁。
- 三档权限按运行冻结，硬拒绝规则始终有效。
- 完全重复工具交换只提示改变策略，不篡改原结果。

### 最后一句总结

> 这个项目的重点不是让模型拥有无限能力，而是让模型在一个由本地程序控制、可观察、可终止的闭环里逐步完成编程任务。
